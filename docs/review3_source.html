1. Complete Working Demonstration & Database Implementation

Rankstack is a contest platform with live leaderboards, real-time submission evaluation, and team management. MongoDB is the primary database for application records. Redis is used alongside MongoDB for leaderboard sorted sets, login sessions, and submission rate limits. A FastAPI backend serves the REST API, and a Next.js 16 client serves the user interface.

The system runs on five MongoDB collections, each configured with $jsonSchema validation and B-tree indexes. The dataset is populated using scripts/seed.py, which loads 112 sample records across all five collections:

Collection Record Count Primary Fields
users 15 name, email, passwordHash, role, totalScore, teamIds
teams 5 name, ownerId, memberIds, totalScore
contests 5 title, description, startTime, endTime, status, problemIds, participants
problems 15 contestId, type (mcq/coding/subjective), difficulty, points, attemptCount
submissions 72 contestId, problemId, submittedBy (user/team), status, score, answer

2. Multi-Document Database Transactions

A contest platform performs mutations that touch multiple documents simultaneously. If one write succeeds while another fails (due to a network interruption or server restart), the database becomes inconsistent. For example, if a submission is inserted but the problem attempt counter fails to increment, problem statistics become inaccurate. Similarly, if a participant's score updates without updating their submission verdict, the leaderboard diverges from the submission record.

To eliminate these risks, Rankstack wraps all multi-document writes inside ACID transactions in api/services.py using PyMongo client sessions. MongoDB supports transactions across multiple collections when running as a replica set (rs0).

2.1 The Transaction Mechanism (run_in_transaction)

Every transaction executes through a centralized runner function that handles session lifecycle and automatic conflict retries:

def run_in_transaction(db: Database, callback: Callable[[ClientSession], T]) -> T:
    with db.client.start_session() as session:
        return session.with_transaction(callback)

MongoDB's session.with_transaction() implements the official retry loop. If a concurrent write causes a TransientTransactionError or an UnknownTransactionCommitResult, PyMongo automatically re-runs the callback function rather than surfacing an unhandled error to the user.

2.2 Core Application Transactions

Rankstack implements four distinct transactional boundaries across its services:

  1. Submission Creation (create_submission):
    • Step 1: Validates that the contest is currently live, within its scheduled start and end window, and that the user is an enrolled participant.
    • Step 2: Inserts the new submission document into db.submissions with status="pending".
    • Step 3: Atomically increments the problem's counter: db.problems.update_one({"_id": problem_id}, {"$inc": {"attemptCount": 1}}).
    • Guaranteed Outcome: A submission record cannot exist without its corresponding attempt counter increment.
  2. Submission Scoring & Total Recalculation (update_submission_status):
    • Step 1: Reads the existing submission within the session to compute the score difference: delta = new_score - old_score.
    • Step 2: Updates the submission document with the new status (e.g. correct) and awarded score.
    • Step 3: Atomically increments the submitter's score in either the users or teams collection: db[target].update_one({"_id": refId}, {"$inc": {"totalScore": delta}}).
    • Step 4: If delta != 0, increments the contest version counter in dirty_leaderboards to signal that the Redis cache must reflect the change.
    • Guaranteed Outcome: A user's total score always matches the exact sum of points awarded across their submissions.
  3. Team Creation (create_team):
    • Step 1: Verifies that all member user IDs exist in the users collection.
    • Step 2: Inserts the new team document into db.teams.
    • Step 3: Updates each member's user document simultaneously using db.users.update_many() with $addToSet: {"teamIds": team_id}.
    • Guaranteed Outcome: A team record cannot exist without mutual back-references on all member profiles.
  4. Team Membership Updates (add_team_member / remove_team_member):
    • Atomically adds or removes the user ID from teams.memberIds and updates users.teamIds within the same session. If an invalid member or team is passed, all updates roll back.

3. Advanced Queries and Analytics (Five Aggregation Pipelines)

MongoDB's aggregation framework calculates totals, averages, and groupings across collections without pulling raw documents into application memory. Below is each pipeline explained stage by stage with real query code and execution results:

Pipeline 1: Contest Leaderboard with Window Ranking (/aggregations/leaderboard/{id})

Groups scored submissions by participant, calculates total points, and sorts competitors descending:

pipeline = [
    {"$match": {"contestId": contest_id, "score": {"$exists": True, "$ne": 0}}},
    {"$group": {
        "_id": {"refId": "$submittedBy.refId", "refType": "$submittedBy.refType"},
        "totalScore": {"$sum": "$score"}
    }},
    {"$project": {"_id": 0, "refId": "$_id.refId", "refType": "$_id.refType", "totalScore": 1}},
    {"$sort": {"totalScore": -1, "refId": -1}},
    {"$limit": 10}
]
# Output:
{'refId': '6ad65ef678cdc32a6e2e361b', 'refType': 'user', 'totalScore': 60.0, 'submissionCount': 3}
{'refId': '6ad65ef678cdc32a6e2e3628', 'refType': 'team', 'totalScore': 50.0, 'submissionCount': 3}

Pipeline 2: Average Score by Difficulty Tier via $lookup (/aggregations/avg-score-by-difficulty)

Computes average score per problem, joins with the problems collection, and averages by difficulty:

pipeline = [
    {"$group": {"_id": "$problemId", "avgScore": {"$avg": "$score"}}},
    {"$lookup": {"from": "problems", "localField": "_id", "foreignField": "_id", "as": "problem"}},
    {"$unwind": "$problem"},
    {"$group": {
        "_id": "$problem.difficulty",
        "avgScorePerProblem": {"$avg": "$avgScore"},
        "problemCount": {"$sum": 1}
    }},
    {"$project": {"_id": 0, "difficulty": "$_id", "avgScorePerProblem": 1, "problemCount": 1}}
]
# Output:
{'difficulty': 'easy',   'problemCount': 3, 'avgScorePerProblem': 5.21}
{'difficulty': 'medium', 'problemCount': 3, 'avgScorePerProblem': 11.67}
{'difficulty': 'hard',   'problemCount': 3, 'avgScorePerProblem': 18.75}

Pipeline 3: Submission Status Breakdown per Contest (/aggregations/submission-status-by-contest)

Facets submission verdicts (correct, incorrect, partial, pending) across contests in a two-tier group:

pipeline = [
    {"$group": {"_id": {"contestId": "$contestId", "status": "$status"}, "count": {"$sum": 1}}},
    {"$group": {"_id": "$_id.contestId", "statusCounts": {"$push": {"status": "$_id.status", "count": "$count"}}}},
    {"$lookup": {"from": "contests", "localField": "_id", "foreignField": "_id", "as": "contest"}},
    {"$unwind": "$contest"},
    {"$project": {"_id": 0, "contestId": "$_id", "title": "$contest.title", "statusCounts": 1}}
]
# Output: Contest: 'Streamlined modular infrastructure Contest'
Status Counts: [{'status': 'correct', 'count': 13}, {'status': 'incorrect', 'count': 6}, {'status': 'partial', 'count': 3}]

Pipeline 4: Distinct Problems Solved per User (/aggregations/problems-solved-per-user)

Uses $addToSet to isolate unique problem IDs solved correctly, preventing duplicate point counting:

pipeline = [
    {"$match": {"status": "correct", "submittedBy.refType": "user"}},
    {"$group": {"_id": "$submittedBy.refId", "problemsSolved": {"$addToSet": "$problemId"}}},
    {"$project": {"_id": 0, "userId": "$_id", "distinctProblemsSolved": {"$size": "$problemsSolved"}}},
    {"$lookup": {"from": "users", "localField": "userId", "foreignField": "_id", "as": "user"}},
    {"$unwind": "$user"},
    {"$project": {"userId": 1, "name": "$user.name", "distinctProblemsSolved": 1}},
    {"$sort": {"distinctProblemsSolved": -1}}
]
# Output:
{'name': 'Daniel Wagner', 'distinctProblemsSolved': 7} | {'name': 'Connie Lawrence', 'distinctProblemsSolved': 5}

Pipeline 5: Team Performance via Correlated Subquery $lookup (/aggregations/team-performance)

Performs a correlated subquery $lookup into submissions matching team memberIds:

pipeline = [
    {"$lookup": {
        "from": "submissions",
        "let": {"memberIds": "$memberIds"},
        "pipeline": [{"$match": {"$expr": {"$and": [
            {"$eq": ["$submittedBy.refType", "user"]},
            {"$in": ["$submittedBy.refId", "$$memberIds"]}
        ]}}}],
        "as": "memberSubmissions"
    }},
    {"$addFields": {
        "totalScore": {"$sum": "$memberSubmissions.score"},
        "submissionCount": {"$size": "$memberSubmissions"},
        "memberCount": {"$size": "$memberIds"}
    }},
    {"$project": {"name": 1, "totalScore": 1, "submissionCount": 1, "memberCount": 1}}
]
# Output: Team: 'Team Darkgreen Husband' | Members: 3 | Total Submissions: 27 | Combined Score: 365.0 pts

4. Ephemeral Storage (Redis)

Redis 7 handles high-frequency reads and transient state alongside MongoDB:

  • Live Leaderboard: Stored as a sorted set (ZSET). Scores update via ZINCRBY on judged submissions. Reading top participants via ZREVRANGE takes sub-millisecond memory time.
  • Session Management: Opaque 32-byte tokens are stored with SETEX and automatic 3600-second expiration, avoiding database cleanup jobs.
  • Rate Limiting: Atomic key increments enforce a cap of 10 submissions per 60-second window.
  • Cache Reconciliation: If Redis restarts, the API checks MongoDB's dirty_leaderboards version, runs the aggregation pipeline to rebuild the sorted set, and updates the cache.
