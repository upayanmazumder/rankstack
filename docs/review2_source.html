02Database Implementation

2.1 Collections & relationships

The five collections from the Review 1 design were implemented as-is in MongoDB, with every relationship expressed as an ObjectId reference (never embedded, except contests.participants, which stays a small array of refs since it is always read alongside its parent contest).

users
_id, name, email (unique idx),
passwordHash, role, totalScore,
teamIds[], createdAt
teams
_id, name, memberIds[],
totalScore, createdAt
contests
_id, title, description,
startTime, endTime, status,
createdBy, problemIds[],
participants[], createdAt
problems
_id, contestId, type,
title, difficulty, points,
attemptCount, + type-specific
fields, createdAt
submissions
_id, contestId, problemId,
submittedBy{refType,refId},
answer, status, score,
submittedAt

Relationships implemented: User→Contest (embedded ref array), Contest→Problems (problems.contestId), User/Team→Submission (submittedBy), Submission→Problem (problemId), Team→Users (memberIds), and a User→Team back-reference (users.teamIds) added for the team-membership transaction in §4.3.

2.2 Schema validation ($jsonSchema)

Every collection is created with a MongoDB $jsonSchema validator (app/db.py). The problems collection additionally uses a oneOf clause so the database itself enforces different required fields per polymorphic type — a direct NoSQL-level expression of the Review 1 polymorphic design:

# app/db.py — problems validator (excerpt)
"oneOf": [
  {"properties": {"type": {"enum": ["mcq"]}, "options": {...}, "correctAnswer": {...}},
   "required": ["options", "correctAnswer"]},
  {"properties": {"type": {"enum": ["coding"]}, "testCases": {...}},
   "required": ["testCases"]},
  {"properties": {"type": {"enum": ["subjective"]}, "evaluationRubric": {...}},
   "required": ["evaluationRubric"]},
]
Live verification Inserting an mcq document missing options/correctAnswer → pymongo.errors.WriteError (rejected by MongoDB itself). Inserting the same document with those fields present → accepted. Confirmed against all 5 collections.

4.3 Transactions (3, on a single-node replica set)

MongoDB transactions require a replica set — a standalone mongod does not support start_transaction(). docker-compose.yml runs mongod --replSet rs0 with a one-shot rs.initiate() container. All three transactions live in app/services.py and are used by both the API and the seed script (so denormalized counters stay consistent with the raw submission data everywhere):

  1. create_submission — insert a submission + atomically increment problems.attemptCount.
  2. update_submission_status — update a submission's status/score + atomically apply the score delta to the submitter's cached totalScore on users/teams.
  3. add_team_member / remove_team_member — update teams.memberIds + users.teamIds back-reference atomically.
# app/services.py — transaction #1 (excerpt)
with client.start_session() as session:
    with session.start_transaction():
        result = db["submissions"].insert_one(doc, session=session)
        db["problems"].update_one({"_id": problem_id},
                                   {"$inc": {"attemptCount": 1}}, session=session)
Live evidence — before/after counters, via scripts/demo.py 
problem.attemptCount before=7 after=8   (submission inserted atomically)
user.totalScore       before=90 after=100 (status+score updated atomically)

06Intermediate Demonstration

scripts/demo.py (make demo) is a self-cleaning script a faculty member can run live end-to-end. It connects to the real database and prints, in order: a CRUD round-trip, an indexed query with .explain() proof, a multi-document transaction with before/after counters, all 5 aggregation results, and the Redis leaderboard/session/rate-limit state — verified twice end-to-end from a completely clean slate (docker compose down -v && make up && make init-db && make seed && make demo), and again against a live uvicorn server via curl for the CRUD/Redis evidence captured in this document.
